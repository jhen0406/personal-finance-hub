# Personal Finance Hub — 產品規格（SPEC）

> 狀態：草稿 v0.1｜最後更新：2026-11-26
> 本文件是開發的唯一依據。若與 README 內容衝突，以本文件為準。

---

## 1. 產品目標

### 1.1 要解決的問題

擁有多張信用卡的使用者，各卡的**結帳日、繳款日、扣款帳戶都不同**，必須在多個銀行 App 之間切換才能掌握何時要付多少錢，容易忘記繳款或扣款帳戶餘額不足。

### 1.2 核心價值（v0.1 只驗證這件事）

在 LINE 裡**快速記帳**，系統依記帳資料**估算每張卡的帳單金額**，並在**付款月曆**上集中呈現，於繳款日前透過 LINE **主動提醒**。

### 1.3 非目標（v0.1 明確不做）

- 不追蹤銀行帳戶的真實餘額、不計算總資產
- 不串接任何銀行或信用卡 API，所有資料由使用者手動輸入
- 不處理分期付款、外幣消費、退款與預借現金
- 不處理銀行因假日順延的繳款日

## 2. 名詞定義

| 名詞                             | 定義                                                                                      |
| -------------------------------- | ----------------------------------------------------------------------------------------- |
| **MINI App**                     | 在 LINE 內開啟的 web app（LINE MINI App，以 LIFF SDK 開發），本系統所有使用者介面都在這裡 |
| **結帳日**（closing day）        | 每月固定的日期（1–31），決定一筆消費屬於哪一期帳單                                        |
| **繳款日**（payment day）        | 每月固定的日期（1–31），該期帳單的最後繳款日或自動扣款日                                  |
| **帳單週期**（statement period） | 從上期結帳日的隔天，到本期結帳日（含）的期間                                              |
| **估算帳單金額**                 | 系統依帳單週期內的記帳資料加總而得，**不保證等於銀行實際帳單**                            |
| **扣款帳戶**                     | 純標籤（例如「台新薪轉戶」），表示帳單預計從哪個帳戶扣款，**不記錄餘額**                  |
| **付款方式**                     | 現金、信用卡（須指定哪張卡）、轉帳、電子支付                                              |
| **電子支付**                     | 行動支付與儲值卡的統稱，例如 LINE Pay、icash Pay、街口支付、悠遊卡                        |
| **支付工具**（wallet）           | 使用者登錄的某一個電子支付，例如「LINE Pay」「悠遊卡」                                    |
| **扣款來源**（funding source）   | 電子支付這筆錢實際從哪裡出：信用卡（須指定哪張卡）、錢包餘額、銀行帳戶                    |
| **消費類別**                     | 使用者可自訂的分類，包含名稱與標籤顏色                                                    |

## 4. 使用者故事與驗收條件（v0.1）

驗收條件（AC）用 Given / When / Then 撰寫，之後可直接轉成測試案例。

### US-01 LINE 登入

> 身為使用者，我想用 LINE 帳號直接使用服務，不需要另外註冊。

- **AC-01-1**：Given 使用者首次從圖文選單開啟 MINI App，When MINI App 完成 LINE 登入，Then 系統以 LINE user ID 建立使用者，並為他建立預設消費類別（見 US-08），然後進入對應頁面。
- **AC-01-2**：Given 使用者已存在，When 再次開啟 MINI App，Then 不會重複建立使用者。
- **AC-01-3**：後端**必須在伺服器端驗證** MINI App 傳來的 ID token，不可信任前端直接傳送的 user ID。
- **AC-01-4**：所有 API 只能存取目前登入使用者自己的資料。存取他人資料時回傳 404（不洩漏資源是否存在）。

### US-02 記一筆消費

> 身為使用者，我想從 LINE 圖文選單快速記下一筆消費。

**欄位：**

| 欄位     | 必填   | 規則                                                                                                               |
| -------- | ------ | ------------------------------------------------------------------------------------------------------------------ |
| 消費日期 | ✅     | 預設今天（Asia/Taipei），不可晚於今天                                                                              |
| 金額     | ✅     | 正整數（新台幣元），1 ～ 9,999,999                                                                                 |
| 類別     | ✅     | 從使用者自己未封存的類別中選擇（見 US-08），選項旁顯示標籤顏色                                                     |
| 項目     | ✅     | 文字，1–50 字，去除前後空白後不可為空                                                                              |
| 付款方式 | ✅     | 現金／信用卡／轉帳／電子支付                                                                                       |
| 支付工具 | 條件式 | 付款方式為「電子支付」時必填，從自己未封存的支付工具中選擇（見 US-09）；其他付款方式不可填                         |
| 扣款來源 | 條件式 | 付款方式為「電子支付」時必填：信用卡／錢包餘額／銀行帳戶。選好支付工具後，預設帶入該工具的預設扣款來源             |
| 信用卡   | 條件式 | 付款方式為「信用卡」，或付款方式為「電子支付」且扣款來源為「信用卡」時必填，只能選擇自己未封存的卡；其他情況不可填 |

**範例**：

- 用 LINE Pay 綁國泰 CUBE 卡付款 → 付款方式：電子支付，支付工具：LINE Pay，扣款來源：信用卡，信用卡：國泰 CUBE。**這筆會算進 CUBE 卡的帳單**
- 用悠遊卡搭捷運 → 付款方式：電子支付，支付工具：悠遊卡，扣款來源：錢包餘額
- Apple Pay、Google Pay 是直接刷綁定的信用卡，請選付款方式「信用卡」，不需要建立成支付工具

- **AC-02-1**：Given 欄位皆合法，When 送出，Then 儲存成功，顯示成功訊息，表單重置並保留上次選擇的付款方式、支付工具、扣款來源與信用卡。
- **AC-02-2**：Given 任一欄位不合法，When 送出，Then 不儲存，並在該欄位旁顯示錯誤原因。
- **AC-02-3**：Given 使用者尚未建立任何信用卡或支付工具，When 選到需要它的選項，Then 提示前往新增。
- **AC-02-4**：前端驗證只是輔助，**後端必須做相同的驗證**，包含上表所有條件式必填與不可填的規則。

### US-03 查看、編輯、刪除交易紀錄

> 身為使用者，我想修正記錯的消費。

- **AC-03-1**：可依月份瀏覽交易列表，依消費日期由新到舊排序。
- **AC-03-2**：可編輯交易的所有欄位，驗證規則與 US-02 相同。
- **AC-03-3**：刪除前需二次確認，刪除後無法復原（v0.1 不做復原）。
- **AC-03-4**：編輯或刪除信用卡交易後，該卡的估算帳單金額與剩餘額度立即反映變更。

### US-04 管理扣款帳戶

> 身為使用者，我想建立「台新薪轉戶」這類標籤，標示每張卡從哪個帳戶扣款。

- **欄位**：暱稱（必填，1–20 字，同一使用者內不可重複）。
- **AC-04-1**：可新增、改名、刪除帳戶。
- **AC-04-2**：Given 帳戶正被任一信用卡設為扣款帳戶，When 嘗試刪除，Then 拒絕並列出引用它的信用卡。

### US-05 管理信用卡

> 身為使用者，我想登錄每張信用卡的結帳日、繳款日與額度。

**欄位：**

| 欄位       | 必填 | 規則                                            |
| ---------- | ---- | ----------------------------------------------- |
| 暱稱       | ✅   | 1–20 字，同一使用者內不可重複（未封存的卡之間） |
| 卡號末四碼 | ✅   | 剛好 4 位數字。**系統不得儲存完整卡號**         |
| 信用額度   | ❌   | 正整數；未填則不顯示剩餘額度                    |
| 結帳日     | ✅   | 1–31                                            |
| 繳款日     | ✅   | 1–31，不可等於結帳日                            |
| 扣款帳戶   | ❌   | 選擇自己的帳戶                                  |
| 繳費提醒   | ✅   | 開／關，預設開；設定方式見 US-07                |

- **AC-05-1**：可新增、編輯信用卡。
- **AC-05-2**：信用卡**不提供硬刪除**，只能「封存」。封存後不出現在記帳選單、月曆與提醒中，但歷史交易保留。
- **AC-05-3**：卡片詳情顯示：本期帳單週期、本期累計消費、上期估算帳單金額與繳款日、剩餘額度（有設定額度時）。
- **AC-05-4**：修改結帳日或繳款日後，帳單週期與月曆依新設定重新計算（v0.1 不保留歷史設定）。

### US-06 付款月曆

> 身為使用者，我想在一個月曆上看到這個月所有要繳的卡費。

- **AC-06-1**：以月為單位顯示，可切換上／下個月。
- **AC-06-2**：每張未封存信用卡的繳款日標示在月曆上，點選後顯示：卡片暱稱、估算帳單金額、扣款帳戶。
- **AC-06-3**：同一天有多張卡時，該日顯示筆數，點選後列出全部。
- **AC-06-4**：月曆下方提供當月應繳清單，依繳款日排序，並顯示當月估算總額。
- **AC-06-5**：估算金額旁需標示「估算」，避免使用者誤認為銀行實際帳單金額。

### US-07 繳費提醒

> 身為使用者，我想在繳款日前收到 LINE 提醒，以便確認扣款帳戶餘額是否足夠。

- **設定**：每張卡可勾選要在繳款日的哪幾天前提醒，選項為：7、5、3、1 天前、當天，可複選，預設為「3 天前」與「當天」。
- **AC-07-1**：系統每天 **09:00–10:00（Asia/Taipei）之間**執行一次檢查，對符合條件的卡發送 LINE 推播（時間區間來自部署平台的排程限制，見 ADR 0001）。
- **AC-07-2**：同一使用者同一天有多張卡要提醒時，**合併成一則訊息**（節省推播額度）。
- **AC-07-3**：訊息內容包含：卡片暱稱、繳款日、估算帳單金額、扣款帳戶，以及開啟月曆的連結。
- **AC-07-4**：估算帳單金額為 0 的卡不發送提醒。
- **AC-07-5**：**冪等性**：同一張卡、同一期帳單、同一個提醒時間點，最多只發送一次；排程重跑也不會重複發送。
- **AC-07-6**：推播失敗時記錄錯誤，不影響其他使用者的推播。
- **AC-07-7**：使用者封鎖官方帳號後，推播失敗不視為系統錯誤。

### US-08 管理消費類別

> 身為使用者，我想新增自己的消費類別，並用顏色區分。

**欄位：**

| 欄位     | 必填 | 規則                                                   |
| -------- | ---- | ------------------------------------------------------ |
| 名稱     | ✅   | 1–10 字，同一使用者未封存的類別之間不可重複            |
| 標籤顏色 | ✅   | `#RRGGBB` 格式。介面提供 12 色色盤供選擇，後端驗證格式 |

**預設類別**（使用者建立時自動產生，之後可以改名、改色、封存，和自訂類別沒有差別）：

| 名稱 | 顏色      |
| ---- | --------- |
| 餐飲 | `#F97316` |
| 交通 | `#3B82F6` |
| 購物 | `#EC4899` |
| 娛樂 | `#8B5CF6` |
| 居住 | `#14B8A6` |
| 醫療 | `#EF4444` |
| 教育 | `#EAB308` |
| 其他 | `#6B7280` |

- **AC-08-1**：可新增類別、修改名稱與顏色，並可調整在記帳選單中的排列順序。
- **AC-08-2**：類別**不提供硬刪除**，只能封存。封存後不出現在記帳選單中，但歷史交易仍顯示原本的名稱與顏色。
- **AC-08-3**：修改類別名稱或顏色後，所有使用該類別的歷史交易一併顯示新的名稱與顏色。
- **AC-08-4**：使用者至少要保留一個未封存的類別，封存最後一個時拒絕。

### US-09 管理電子支付工具

> 身為使用者，我想登錄常用的行動支付與儲值卡，並設定它預設從哪裡扣款。

**欄位：**

| 欄位         | 必填   | 規則                                                                                                                                           |
| ------------ | ------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 名稱         | ✅     | 1–20 字，同一使用者未封存的支付工具之間不可重複。新增時可從建議清單選擇（LINE Pay、icash Pay、街口支付、全支付、悠遊卡、一卡通），也可自行輸入 |
| 預設扣款來源 | ❌     | 信用卡／錢包餘額／銀行帳戶，用來在記帳時自動帶入                                                                                               |
| 預設信用卡   | 條件式 | 預設扣款來源為「信用卡」時必填                                                                                                                 |

- **AC-09-1**：可新增、編輯支付工具。
- **AC-09-2**：支付工具**不提供硬刪除**，只能封存，規則同 AC-05-2。
- **AC-09-3**：預設值只影響記帳表單的帶入值，修改預設值**不會**改動已存在的交易。
- **AC-09-4**：Given 支付工具的預設信用卡被封存，Then 該工具的預設扣款來源清空，記帳時需重新選擇。

## 5. 業務規則

### 5.1 日期與時區

- 所有日期判斷一律使用 **Asia/Taipei**。
- 交易只記日期，不記時間。
- 結帳日或繳款日大於當月天數時，以**當月最後一天**為準（例如設定 31 日，2 月就是 28 或 29 日）。

### 5.2 帳單週期計算

設結帳日為 `C`，某月份的實際結帳日記為 `closing(年, 月)`（套用 5.1 的月底規則）。

- 一筆消費日期為 `d`，它屬於**第一個 ≥ d 的結帳日**所對應的那一期帳單。
- 帳單週期 = 上一期結帳日的隔天 ～ 本期結帳日（含）。

### 5.3 繳款日計算

設繳款日為 `P`，某期帳單的結帳日落在 `Y 年 M 月`：

- 若 `P > C`：繳款日在**同月** `Y/M/P`
- 若 `P < C`：繳款日在**次月** `Y/(M+1)/P`

（同樣套用 5.1 的月底規則）

- **邊界保護**：若套用月底規則後，繳款日 ≤ 結帳日（例如結帳日 28 日、繳款日 30 日，在 2 月會變成 2/28 結帳、2/28 繳款），則繳款日改為次月的 `P`。

**範例**：結帳日 5 日、繳款日 20 日 → 11/6～12/5 的消費，在 12/20 繳款。
**範例**：結帳日 25 日、繳款日 10 日 → 10/26～11/25 的消費，在 12/10 繳款。

### 5.4 估算帳單金額

- = 該期帳單週期內，所有 `credit_card_id` 為該卡的交易金額加總。
- 這同時涵蓋「直接刷卡」與「電子支付且扣款來源為該卡」兩種情況，計算邏輯不需要判斷付款方式。
- **v0.1 已知限制**：用信用卡替錢包加值（例如悠遊卡自動加值）的金額不會出現在估算帳單中，因為花用時記的是「錢包餘額」。v0.2 的加值紀錄會解決這個問題。在那之前，記帳介面不提供特別的處理方式。

### 5.5 剩餘額度

- 已用額度 = 所有「繳款日 ≥ 今天」的帳單金額，加上目前尚未結帳的本期消費。
- **假設**：繳款日過後視為已繳清（v0.1 不記錄實際繳款）。
- 剩餘額度 = 信用額度 − 已用額度，可為負數（顯示為超額）。

### 5.6 金額

- 一律以**整數（新台幣元）**儲存與計算，不使用浮點數。

> ⚠️ 5.2～5.5 是最容易出錯的核心邏輯，必須有完整的單元測試，涵蓋：月底（28/29/30/31 日）、跨年（12 月→1 月）、閏年、P < C 跨月、交易剛好落在結帳日當天。

## 6. 資料模型草稿（v0.1）

> 實際型別依選定的資料庫調整。所有資料表都有 `created_at`、`updated_at`。

**users**

| 欄位         | 型別           | 說明          |
| ------------ | -------------- | ------------- |
| id           | PK             |               |
| line_user_id | string, unique | LINE user ID  |
| display_name | string         | LINE 顯示名稱 |

**accounts**（扣款帳戶標籤）

| 欄位     | 型別       | 說明                      |
| -------- | ---------- | ------------------------- |
| id       | PK         |                           |
| user_id  | FK → users |                           |
| nickname | string     | unique(user_id, nickname) |

**credit_cards**

| 欄位             | 型別                    | 說明                        |
| ---------------- | ----------------------- | --------------------------- |
| id               | PK                      |                             |
| user_id          | FK → users              |                             |
| nickname         | string                  |                             |
| last4            | char(4)                 | 只存末四碼                  |
| credit_limit     | int, nullable           |                             |
| closing_day      | smallint                | 1–31                        |
| payment_day      | smallint                | 1–31，≠ closing_day         |
| debit_account_id | FK → accounts, nullable |                             |
| reminder_enabled | bool                    | 預設 true                   |
| reminder_offsets | int[]                   | 繳款日前幾天，例如 `[3, 0]` |

## 7. 非功能需求

### 7.1 安全性

- 不儲存完整卡號、CVV、有效期限，也不儲存任何銀行帳號。
- LINE Channel secret 與 access token 只放在環境變數，不進版本控制。
- 每個 API 都在後端驗證身分，並以 `user_id` 過濾資料。
- 所有輸入在後端驗證；資料庫存取一律使用參數化查詢或 ORM。

### 7.2 LINE 平台限制

- 推播（push message）有每月免費則數上限，依官方帳號方案而定，這也是 AC-07-2 要合併訊息的原因。
- 聊天訊息（Flex Message）無法繪製圖表，所以 v0.2 的統計圖表要做在 MINI App 裡。
- MINI App channel 只能放一個 web app，所有頁面以前端路由區分，圖文選單的按鈕連到不同路徑。
- MINI App channel 與 Messaging API channel **必須建在同一個 Provider 底下**，同一個使用者在兩邊才會拿到相同的 LINE user ID。

### 7.3 可用性

- MINI App 頁面以手機為主（寬度 360px 以上）。
- 記帳表單從開啟到送出，目標在 15 秒內完成。

### 7.4 可維護性

- 帳單週期、繳款日、剩餘額度的計算邏輯寫成**純函式**，不依賴資料庫與目前時間（「今天」由參數傳入），方便測試。

## 8. v0.2 需求摘要（開發前再細化）

- **統計**：MINI App 頁面，以圓餅圖加圖例呈現，可依類別（使用類別的標籤顏色）、付款方式、支付工具或信用卡分組，並依週、月、年篩選；圖文選單新增「統計」按鈕。
- **每月預算**：設定每月總預算。當月消費達 80% 以上時，每次記帳成功後顯示提醒文字，新的月份開始後自動消失。
- **固定開銷**：欄位包含類別、項目、**金額**、付款方式（含指定信用卡）、週期（週／月／年）、**扣款日**、**起始日**、結束日（選填）。顯示在付款月曆上；付款方式為信用卡時，是否自動產生交易需再定義。
- **錢包加值紀錄**：欄位包含支付工具、加值日期、金額、加值來源（現金／信用卡（須指定卡）／銀行帳戶），並支援標記「自動加值」。加值**不算消費**，不計入統計與預算；但加值來源為信用卡時，**要算進該卡的估算帳單與已用額度**。資料模型預計新增 `wallet_top_ups` 表，5.4 的帳單公式改為「消費加總＋加值加總」。
